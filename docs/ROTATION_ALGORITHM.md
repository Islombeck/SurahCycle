# Алгоритм ротации

## Назначение

Алгоритм заменяет ручные галочки и `x`: он хранит фактическую историю отдельно от нормализованного баланса и показывает пользователю только текущую потребность в повторении.

## Версионируемая модель частей

У каждой выученной суры есть активная `SurahRotationScheme` версии `v`. Она содержит от 1 до `ayahCount` частей с устойчивыми id и непрерывными диапазонами аятов. Диапазоны строго покрывают всю суру: первая часть начинается с 1, последняя заканчивается проверенным `ayahCount`, а соседние части соприкасаются без пробелов и пересечений.

Для части `p` хранятся проекции `scoreₚ`, `recitationCountₚ` и `lastUsedAtₚ`. Состояние суры выводится так:

```text
effectiveScore(surah) = min(scoreₚ)
fullEquivalentTotal(surah) = min(recitationCountₚ)
rawRemaining(surah) = rotationTarget - effectiveScore(surah)
```

Минимум означает, что полным повторением считается только комплект, в котором каждая часть получила очередной credit. Сумма part credits и число пользовательских действий показываются отдельно и не выдаются за полные прочтения.

`RecitationEvent` — одно атомарное действие. Его coverage может включать одну часть, несколько частей или все части текущей схемы; каждую выбранную часть событие увеличивает ровно на один независимо от `rakaatSpanCount`. Для неразделённой суры «вся сура» — единственная часть.

Смена диапазонов никогда не редактирует старую схему. Создаётся версия `v+1`, её части получают baseline/carry текущего эффективного состояния, а все старые события продолжают ссылаться на прежние part ids. При rebuild версии воспроизводятся по порядку, поэтому удаление старого события корректно переносит изменившийся carry в последующие схемы.

## Термины

- `rotationTarget` (`T`) — глобальный уровень текущего цикла. Начальное значение: **1**.
- `rotationScore` (`Sᵢ`) — эффективный баланс суры, то есть минимум scores её активных частей.
- `totalRecitations` — full-equivalent total, то есть минимум part counts. Число неудалённых действий и part credits — отдельные метрики.
- `activeSurahs` (`A`) — суры, участвующие в текущей ротации и рекомендациях.
- `rawRemainingᵢ = T - Sᵢ`.
- `remainingᵢ = max(rawRemainingᵢ, 0)` — потребность для основного UI.

Интерпретация:

| Условие | UI | Смысл |
|---|---|---|
| `rawRemaining == 1` | пустая галочка | нужно одно прочтение |
| `rawRemaining > 1` | `N×` | нужно N прочтений |
| `rawRemaining == 0` | зелёная галочка | текущий цикл закрыт ровно |
| `rawRemaining < 0` | `-x`, `-2x`, … | сура прочитана вперёд |

Опережение (`rawRemaining < 0`) показывается прямо в строке главного экрана. Оно исчезает по мере роста глобальной цели и не нормализуется искусственно.

## Инициализация и членство

Глобальное состояние начинается с `rotationTarget = 1`.

При **первом** добавлении новой выученной суры:

```text
rotationScore = rotationTarget - 1
totalRecitations = 0
isActive = true
```

То есть новая сура входит с одним требуемым повторением и не наследует долг прошлых циклов.

Правила активности:

- отключение исключает суру из `A`, но сохраняет её `rotationScore` и историю;
- повторное включение возвращает сохранённый score — оно не выполняет rebasing к `target - 1`;
- первое включение, отключение и повторное включение сами по себе **не меняют** `rotationTarget` и не запускают проверку завершения цикла;
- если `A` пусто, target не изменяется: пустое множество не считается завершённым циклом.

## Регистрация прочтения

Операция выполняется атомарно для активной суры:

```text
preAction = snapshot(currentState)
append RecitationEvent + exact part coverage
for each covered part: part.score += 1
surah.rotationScore = min(activeScheme.part.score)

if activeSurahs.isNotEmpty
   and every(activeSurah.rotationScore >= rotationTarget):
    rotationTarget += 1
```

Важно: за одну регистрацию `rotationTarget` может вырасти **максимум на 1**. Здесь нет `while`. Даже если после увеличения все активные score всё ещё выше нового target, следующий переход возможен только после следующего зарегистрированного прочтения.

`totalRecitations` не инкрементируется как независимая истина. После добавления события его проекция становится минимумом recitation counts частей активной схемы. Число неудалённых событий остаётся отдельным action count.

## Почему target проверяется только после чтения

Цикл — результат фактического чтения, а не редактирования списка. Поэтому:

- удаление отстающей суры из активных не закрывает цикл автоматически;
- включение суры не сдвигает target;
- ручная корректировка баланса не сдвигает target;
- условие проверяется после следующего успешного `RecitationEvent`;
- за это действие всё равно разрешён только один переход.

## Примеры

### Первый цикл

```text
T = 1
A: score 0
B: score 0
```

После чтения A: `A=1`, `B=0`, `T=1`. После чтения B: `A=1`, `B=1`; все достигли цели, поэтому `T=2`. Теперь обеим требуется по одному чтению.

### Повтор одной суры раньше остальных

```text
T = 2
A = 3
B = 0
```

Для A `rawRemaining=-1`, она впереди. Для B `rawRemaining=2`, UI показывает `2×`. Исторические чтения A не сбрасываются и её score не нормализуется вниз.

### Новая сура в большом цикле

```text
T = 31
new C.score = 30
```

C требует одно чтение, а не 31. Её `totalRecitations` равен нулю, пока нет реального события.

### Отключение и возврат

При `T=8`, `A.score=6` отключение A сохраняет `6`. Повторное включение возвращает A с тем же score и долгом `2`; ни одна из операций не меняет `T`.

## Ручная корректировка баланса

Техническая миграция из Google Tasks записывается как отдельный `RotationAdjustmentEvent`:

```text
surahId
delta              // например +1 или -1
reason
createdAtUtc
```

Корректировка:

- равномерно меняет score всех частей исторической схемы, поэтому effective `rotationScore` сдвигается на тот же `delta`;
- не создаёт прочтение и не меняет `totalRecitations`;
- не запускает повышение target;
- доступна только в расширенных настройках и требует явного подтверждения;
- остаётся в журнале, чтобы rebuild дал тот же результат.

## Хранение и rebuild

Стратегия Sprint 2 — **snapshot + event journal + immutable scheme history**.

В журнал входят:

- `RecitationEvent` с монотонным `journalSequence` и tombstone удаления;
- `RotationAdjustmentEvent` с тем же пространством sequence и tombstone удаления.

Назначенный при первом включении score хранится как неизменяемый `activationBaselineScore` в пользовательской записи суры. Текущий флаг активности и порядок также находятся в этой записи. Вместе с versioned scheme baselines этого достаточно для локального rebuild; полноценный membership journal потребуется при будущей multi-device синхронизации.

Snapshot — кеш проекции (`rotationTarget`, scores, active flags, journal cursor, algorithm version). Он ускоряет запуск, но не заменяет журнал.

При rebuild:

1. читаются current mastered rows и их immutable activation baseline;
2. неудалённые чтения и корректировки читаются по `journalSequence`;
3. coverage каждого чтения применяется только к указанным частям его исторической схемы;
4. для каждой схемы вычисляются part counts/scores, а её successor получает пересчитанный carry;
5. корректировка равномерно применяется ко всем частям соответствующей схемы;
6. последнее использование части берётся из последнего retained coverage по sequence;
7. отрицательный результат или журнал для никогда не активированной суры отклоняется как повреждение данных;
8. `rotationTarget` сохраняется не ниже значения до rebuild;
9. snapshot заменяется в той же транзакции.

Target не пытается заново вывести исторический состав активных сур, который пока не журналируется. Монотонный floor — намеренная семантика обычного удаления. Немедленный Undo использует отдельный точный pre-action snapshot.

## Удаление из истории

Удаление произвольного `RecitationEvent` требует подтверждения и всегда запускает rebuild. Для статистики удалённое событие перестаёт входить в action count, все его coverage credits исчезают, а `totalRecitations` заново выводится как минимум part counts.

Для обычного удаления действует монотонность:

```text
rebuiltTarget = max(targetBeforeDeletion, targetObtainedByReplay)
```

То есть удаление старого чтения не отматывает уже достигнутый глобальный цикл. Score удалённой суры и статистика отражают отсутствие события, поэтому при высоком сохранённом target у неё может появиться дополнительный долг. Удаление фиксируется как tombstone/признак исключения, чтобы будущая синхронизация не воскресила событие.

## Undo последней регистрации

Undo — не то же самое, что удаление старой записи. Перед регистрацией сохраняется краткоживущий `preAction snapshot`. Если пользователь сразу нажал `Отменить`:

- созданное событие помечается отменённым либо удаляется в той же локальной операции;
- целиком восстанавливаются score, active state и `rotationTarget` из pre-action snapshot;
- если именно это чтение повысило target, target возвращается к прежнему значению;
- рекомендации и статистические проекции пересчитываются.

Это осознанное исключение из монотонности target: Undo отменяет ещё не принятую пользователем последнюю операцию, а удаление из истории исправляет уже сохранённую историю при сохранении достигнутого цикла.

## Рекомендации

`SurahSuggestionService` рассматривает только активные части с положительным долгом; завершённые и опережающие позиции исключаются. Сортировка:

1. part-specific `remaining` по убыванию;
2. никогда не читавшиеся и затем наиболее давно читавшиеся — первыми;
3. пользовательский `displayOrder`;
4. номер части и стабильный id как финальная ничья.

Показываются до восьми позиций с сохранённым rank `0..7`. Если есть суры с положительным remaining, выполненные не вытесняют их. Рекомендация не запрещает выбрать любую другую активную суру.

## Проверяемые свойства

Unit tests должны покрывать:

- начальный target и пустой active set;
- равные scores;
- отставание на 1 и на 2;
- опережение;
- переход target при достижении всеми активными;
- максимум один переход на событие;
- новую суру посередине большого цикла;
- отключение и повторное включение с сохранением score;
- отсутствие перехода от одной лишь смены активности;
- ручную корректировку без изменения total;
- удаление последнего и произвольного чтения с rebuild;
- монотонный target при удалении;
- точное восстановление pre-action snapshot через Undo.
